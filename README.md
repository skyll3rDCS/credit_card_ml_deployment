# Сервис прогнозирования дефолта по кредитным картам

Работу выполнил: Гаврилов Андрей (М2551187)

## 1. Введение

В рамках данного проекта разработан и внедрен прототип сервиса машинного обучения для прогнозирования дефолта клиентов по кредитным картам. Сервис реализует основные этапы жизненного цикла ML-модели: от обучения и сериализации до развертывания в виде REST API и подготовки к A/B-тестированию.

Проект ориентирован на демонстрацию подходов к построению production-like решений в области кредитного скоринга.

---

## 2. Цель проекта

Целью проекта является разработка масштабируемого сервиса машинного обучения, обеспечивающего:

* прогнозирование вероятности дефолта клиента
* возможность интеграции в промышленную систему
* воспроизводимость результатов
* готовность к экспериментированию (A/B-тестирование моделей)

---

## 3. Описание данных

В проекте используется датасет **Default of Credit Card Clients**:

* [UCI Machine Learning Repository](https://archive.ics.uci.edu/ml/datasets/default+of+credit+card+clients) (первоисточник)
* [Ссылка на Kaggle](https://www.kaggle.com/datasets/uciml/default-of-credit-card-clients-dataset)

Характеристики:

* объем: 30 000 наблюдений
* предметная область: кредитный скоринг
* целевая переменная: `default.payment.next.month` (бинарный признак дефолта)
* признаки:

  * демографические (возраст, пол, образование, семейное положение)
  * финансовые (кредитный лимит)
  * история платежей и задолженностей

## 4. Модель машинного обучения

В качестве базовой модели используется:

* Logistic Regression

Особенности реализации:

* используется `Pipeline` из библиотеки scikit-learn
* выполняется стандартизация признаков с помощью `StandardScaler`
* модель обучается на обучающей выборке с использованием стратифицированного разбиения
* результат сохраняется с помощью `joblib`

Сериализация модели обеспечивает возможность ее последующего использования в сервисе без повторного обучения.

### 4.1 Экспорт в ONNX-ML (обзорно)

Для оптимизации инференса пайплайн scikit-learn можно конвертировать в формат **ONNX** (например, с помощью `skl2onnx` и последующего запуска через **ONNX Runtime**):

* единый формат модели для разных окружений и языков
* возможность ускорения на CPU/GPU без полного стека обучения
* в перспективе - квантизация и развертывание на специализированном железе

В данном учебном проекте инференс выполняется напрямую из `joblib`, переход на ONNX описан как шаг продвинутого production-контура.

Пример реализации конвертации в ONNX совместимо с текущим scikit-learn:

```python
from skl2onnx import convert_sklearn
from skl2onnx.common.data_types import FloatTensorType

bundle = joblib.load("models/model_v1.pkl")
pipeline = bundle["model"]
feature_count = len(bundle["columns"])

initial_type = [("float_input", FloatTensorType([None, feature_count]))]
onnx_model = convert_sklearn(
    pipeline,
    initial_types=initial_type,
    target_opset=12,
)

with open("models/model_v1.onnx", "wb") as f:
    f.write(onnx_model.SerializeToString())
```

## 5. Архитектура системы

### 5.1 Выбор архитектурного подхода

В рамках проекта реализован монолитный сервис, объединяющий:

* загрузку модели
* предобработку данных
* инференс
* API-интерфейс

Обоснование выбора:

* упрощение разработки и отладки
* снижение инфраструктурной сложности
* достаточность для учебного и прототипного сценария

### 5.2 Альтернативный подход: микросервисная архитектура

В промышленной системе возможна декомпозиция на отдельные сервисы:

* сервис инференса модели
* сервис управления экспериментами (A/B-тестирование)
* сервис логирования и мониторинга
* хранилище признаков (Feature Store)

Такой подход повышает масштабируемость и отказоустойчивость, но требует более сложной инфраструктуры.

### 5.3 Брокер сообщений при масштабировании 

При росте нагрузки **брокер очередей** (например, **RabbitMQ**) мог бы использоваться для:

* асинхронной обработки запросов на скоринг (API кладет задачу в очередь, воркеры возвращают результат по callback или через отдельный poll)
* батчевых пересчетов вероятностей дефолта для портфеля без блокировки онлайн-канала
* отложенной записи аудит-логов и событий для риск-аналитики, чтобы не увеличивать задержку ответа клиенту

Текущий монолит обслуживает запросы синхронно; схема с брокером приведена как развитие архитектуры.

## 6. Веб-сервис

Сервис реализован с использованием фреймворка Flask и предоставляет два основных эндпоинта:

### 6.1 GET /health

Назначение:

* проверка работоспособности сервиса.

Ответ:

```json
{"status": "ok"}
```

---

### 6.2 POST /predict

Назначение:

* получение предсказания модели.

Формат запроса:

* JSON-объект, содержащий значения признаков клиента.

Формат ответа:

```json
{
  "prediction": 0,
  "probability": 0.23
}
```

где:

* `prediction` - бинарное решение (0 или 1);
* `probability` - оценка вероятности дефолта.

### 6.3 Примеры запросов (`curl`)

Сервис должен быть запущен локально или в Docker на порту **5000**.

Проверка работоспособности:

```bash
curl -s http://127.0.0.1:5000/health
```

Пример ответа:

```json
{"status":"ok"}
```

Запрос предсказания (набор признаков без столбца `ID` и без целевой переменной `default.payment.next.month`):

```bash
curl -s -X POST http://127.0.0.1:5000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "LIMIT_BAL": 20000,
    "SEX": 2,
    "EDUCATION": 2,
    "MARRIAGE": 1,
    "AGE": 24,
    "PAY_0": 2,
    "PAY_2": 2,
    "PAY_3": -1,
    "PAY_4": -1,
    "PAY_5": -2,
    "PAY_6": -2,
    "BILL_AMT1": 3913,
    "BILL_AMT2": 3102,
    "BILL_AMT3": 689,
    "BILL_AMT4": 0,
    "BILL_AMT5": 0,
    "BILL_AMT6": 0,
    "PAY_AMT1": 0,
    "PAY_AMT2": 689,
    "PAY_AMT3": 0,
    "PAY_AMT4": 0,
    "PAY_AMT5": 0,
    "PAY_AMT6": 0

```

В ответе ожидаются поля `prediction` и `probability`.

### 6.4 Локальный запуск (без Docker)

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
# Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m app.api
```

Сервис слушает `http://127.0.0.1:5000`. Нужен файл **`models/model_v1.pkl`**; при отсутствии модели выполните обучение (из корня проекта, с корректным путем к данным в `models/train_model.py`):

```bash
python models/train_model.py
```

### 6.5 uWSGI и NGINX в production 

Использование uWSGI и NGINX - это стандартная production-связка для веб-приложений:

* **NGINX** - обратный прокси: TLS, балансировка между инстансами приложения, ограничение скорости, при необходимости отдача статики;
* **uWSGI** (альтернативы - Gunicorn, для ASGI - uvicorn) - WSGI-сервер, который запускает воркеры с приложением Flask и принимает запросы от NGINX по протоколу HTTP или uwsgi.

Встроенный сервер Flask (`app.run`) удобен для разработки; в эксплуатации запросы обычно принимает NGINX и передает их во воркеры uWSGI/Gunicorn, что повышает устойчивость и пропускную способность.

## 7. Контейнеризация

Для обеспечения воспроизводимости и переносимости среды используется Docker.

### 7.1 Состав контейнера

Контейнер включает:

* исходный код сервиса
* сериализованную модель
* зависимости (`requirements.txt`)

### 7.2 Сборка и запуск

Ссылка на образ: [skyll3rdcs/credit-card-ml:latest](https://hub.docker.com/r/skyll3rdcs/credit-card-ml)

Для того, чтобы скачать образ необходимо запустить следующую команду:

```bash
docker pull skyll3rdcs/credit-card-ml:latest
```
Сборка образа:

```bash
docker build -t credit-card-ml -f docker/Dockerfile .
```

Запуск контейнера:

```bash
docker run -p 5000:5000 credit-card-ml
```

### 7.3 Docker Compose

Файл `docker-compose.yml` поднимает два сервиса:

* **`ml-service`** - сборка из `docker/Dockerfile`, API доступно на **5000**
* **`nginx`** - контейнер с образом `nginx:latest` на порту **8081** (демонстрация отдельного сетевого компонента в compose; для реального reverse proxy перед приложением требуется своя конфигурация NGINX с `proxy_pass` на `ml-service`)

Запуск стека:

```bash
docker compose up --build
```

Инференс по-прежнему удобно вызывать на `http://127.0.0.1:5000` (как при одиночном контейнере).

## 10. Бизнес-метрики

Помимо стандартных метрик машинного обучения, в проекте возможно рассматреть использование бизнес-метрик

### 10.1 Ожидаемые потери (Expected Loss)

Определяются как:

Expected Loss = Probability of Default * Credit Exposure

Цель: минимизация финансовых потерь.

---

### 10.2 Доля одобренных заявок (Approval Rate)

Показывает:

* долю клиентов, получивших кредит.

Балансирует:

* рост бизнеса
* уровень риска
